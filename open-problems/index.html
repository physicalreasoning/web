Open problems · October 2026

Open problems: starter projects in world-model evaluation

Twelve projects sized for a first contribution, from a day to a few weeks each. Every one comes from a gap our own work left open, and every one is an issue on GitHub where you can claim it, ask questions and post results. None of them has an answer yet; some will end in a negative result, and that is a result we publish.

Each entry gives the question, why it matters, where the code and data are, a concrete first step, and how it would be judged. Research projects are judged the way all our work is: the comparison and its pass rule are written down and pushed before the test data is fetched, the test is scored once, and the outcome is published whichever way it goes. Forecasting against the market (isotherm)

A third forecast source for the station weather model

isotherm · research · one to two weeks · issue #58

Question. Does adding ECMWF's AIFS or IFS improve isotherm's station weather model at the 16:00 day-before read?

Why it matters. The network passed both of its gates (+0.043 nats per ladder over the best EMOS forecast), but going from 338 to 576 stations moved that only from +0.041 to +0.043. FINDINGS §35 concludes that a third forecast source would likely matter more than more sites. The network sees only NBM and GFS MOS today.

Code and data. src/isotherm/wxnet.py, scripts/wx_gate.py, the 576-station corpus (§32); AIFS and IFS from Open-Meteo's archive as forward fetches them (forward/openmeteo.py), from 2025 for AIFS.

First step. On about 50 corpus stations Kalshi does not list, measure each model's error and how much its errors overlap with NBM's and GFS MOS's, as §33 did for LAMP. Work out which run was public at the read, so nothing leaks.

Judged by. A pre-registered forecast-level test on held-out stations: the network with the new input minus without, log score, 95% date-block interval above zero. Adoption then goes through a new sealed forward test, because the Kalshi backtest rows are used up.

An intra-hour benchmark for Bitcoin ladders

isotherm · research · one to two weeks · issue #59

Question. Does free outside data carry information beyond the quote on Kalshi's hourly Bitcoin ladders, read inside the hour before close?

Why it matters. Benchmark v1 (§47) covers 13 series but not Bitcoin, whose hourly ladders open an hour before close, so the fixed 24 h, 6 h and 1 h reads see almost nothing. On index and currency ladders, free real-time prices were already in the book; crypto is untested.

Code and data. scripts/bench/ and src/isotherm/kalshi.py; Kalshi's public API serves one-minute candles (causal-jepa's corpus builder uses them); a free minute-level BTC/USD price.

First step. Pre-register the read times, event sample, outside model and gate before fetching any quote. Check the contract's settlement source and the basis to your price feed.

Judged by. The outside model against the market at its most favourable price inside each quote, log loss per ladder, 95% date-block interval: pass if the lower bound is above zero. Market-only baselines reported regardless.

A commodity model that holds up an hour before close

isotherm · research · a few days of work, a few weeks of waiting · issue #60

Question. Can a better outside model make free futures prices competitive with Kalshi's commodity ladders 6 hours and 1 hour before close?

Why it matters. A parameter-free model on front-month futures beat the market a day out (§49: +0.331 nats per ladder, pre-registered, 516 ladders) and lost badly an hour out (−1.52). The loss is the model's fault: gold and silver settle on spot about 0.5% below the future, and errors an hour out are fat-tailed.

Code and data. scripts/bench/fetch.py, scripts/bench/commodities.py. The current model, evaluate.py, is hashed for a sealed test and must not be edited; the new model goes in a new file.

First step. Add a basis correction and a heavier-tailed spread fit only on earlier events; pre-register a test window starting after the pre-registration date.

Judged by. New model minus the current one at 6 hours, pooled over the six commodity series, 95% date-block interval above zero, on events that close after the pre-registration. Paper profit after fees and slippage reported alongside.

Score the live API's answers

isotherm · infra · good first issue · a few days · issue #61

Question. How good are the answers the live API actually serves?

Why it matters. The typed answers have been scored on backtest rows (§38). The API logs every served answer with the distribution it came from, but nothing scores that log against outcomes yet.

Code and data. src/isotherm/serve.py (the log), scripts/typed_eval.py (the metrics), the existing label code for outcomes.

First step. scripts/score_answers.py: read a log, join settled outcomes, report the §38 metrics per question type, city and model version, with an offline test on a synthetic log.

Judged by. Infra: tests pass in CI, numbers match typed_eval.py on the same distributions, and answers served after their outcome was known are refused.

Sealed forward tests (forward)

Spread-aware weather entries

forward · research · about a week · issue #3

Question. Would EMOS with NBM's own spread, or isotherm's station network, beat forward's best weather entry?

Why it matters. forward's entries set their spread by station and month only. In isotherm, letting the spread follow NBM's published spread was worth +0.04 to +0.05 nats per ladder, the largest single improvement to any input (§26). Neither has been tried in forward.

Code and data. forward/entries.py, scripts/score.py; NBM's spread from isotherm's IEM parsers (src/isotherm/dataset.py).

First step. Get the spread for the 19 stations as it was public at forward's 20:00 UTC read, add the entry, run the dry run.

Judged by. The dry run is exploration (its outcomes are known). The test that counts is a sealed round: the entry minus emos-all, 95% date-block interval above zero, on outcomes after the freeze, if the maintainers add it to a round spec.

Does fine-tuning help a time-series foundation model beat copying?

forward · research · one to two weeks · issue #4

Question. Zero-shot, no released time-series foundation model beats copying the last price on Kalshi's price ladders. Does one beat it after fine-tuning on the underlyings?

Why it matters. In the dry run (2,609 ladders) the models' predicted moves point the right way 49 to 50% of the time. Fine-tuning is the obvious objection to that result, and it is untested.

Code and data. forward/tsfm.py, forward/prices.py, scripts/score_prices.py, the tests in ROUND2.md.

First step. Fine-tune Chronos-Bolt small on hourly history that ends before any scored ladder; write the recipe and cutoff in the issue before scoring.

Judged by. Round 2's rules: log score minus copy at 24 hours, interval above zero (P1); the same with the copy baseline's spread, to test direction (P2). Exploratory on the dry run; a sealed round if it clears it.

Reproduce the price-ladder dry run from forward alone

forward · infra · good first issue · one to three days · issue #2

Question. Can a new contributor reproduce task 2 from a clone of forward?

Why it matters. The dry run reads past ladders from an isotherm checkout's benchmark data, and silently skips any series it cannot find.

Code and data. scripts/score_prices.py, forward/price_ladders.py, which the sealed path already uses.

First step. Make a missing series an error; add a dry-run mode that builds ladders with price_ladders.fetch; update the README.

Judged by. Infra: CI passes, a test covers the error, and both paths give the same scores on the same events. Published results do not change.

Probing learned representations (causal-jepa)

Finish the convergence run that could reopen the programme

causal-jepa · research · compute-bound, days · issue #4

Question. Does more training make the representation worse (finding 8), or was that an artefact of wide readouts?

Why it matters. Finding 8 is part of the criterion that closed the programme. A re-run on a target that can detect learning (finding 22) had one complete seed: four of five readouts ended above their untrained floor. Its gate needs at least two seeds and returned undecidable.

Code and data. scripts/convergence_v2.py --resume --only-seed N; a corpus rebuilt from Kalshi's public API.

First step. Three complete seeds at 19,200 steps on one corpus (rerun seed 0 if you rebuild).

Judged by. The gate already written in the script, unchanged: a final residual lift above 2 pooled standard deviations with a non-decreasing trajectory reverses finding 8.

Does the one surviving lift replicate at ten minutes?

causal-jepa · research · good first issue · a day or two · issue #5

Question. Does the training lift on future realised volatility survive the raw-feature control at a ten-minute horizon, as it does at five?

Why it matters. Finding 21's +0.0278 is the only lift that survived every control. Its own correction notes the ten-minute version "has not been residualised".

Code and data. scripts/residual_probe.py --target fwd_realised_vol --horizon 10; about six minutes on an M2 Max.

First step. Find the strongest raw control at ten minutes and pre-register the run in docs/RESEARCH_PLAN.md.

Judged by. The three conditions that decided findings 14, 17 and 21: residual R² above zero, above the best untrained arm, and a lift above 2 pooled standard deviations.

Headroom on a different asset class, before any training

causal-jepa · research · good first issue · a few days · issue #6

Question. Can the probe targets that failed on hourly crypto ladders rank representations on another asset class?

Why it matters. Every result is on one venue and one asset class. Finding 15 showed a target's usefulness can be measured from raw features in a minute, with no model; running it first would have redirected the programme.

Code and data. scripts/build_corpus.py --series, scripts/horizon_headroom.py; Kalshi's hourly EUR/USD or USD/JPY ladders.

First step. Build a few hundred events for one non-crypto series and run the headroom check.

Judged by. A finding-15 table for the new series, with a decision rule written first: training is worth proposing only if a future target is discriminative.

Run the experiments on a locally rebuilt corpus

causal-jepa · infra · good first issue · about a day · issue #7

Why it matters. The library finds a local corpus, but most scripts default to a sibling checkout of the original data repository, which contributors do not have.

Code and data. causaljepa/data.py and the --pm-jepa-root default in scripts/.

Evaluating under intervention

Design an intervention test for world models

new · research · a design in days, an experiment in weeks · issue #5

Question. Can we build a small, reproducible test of whether a model's predicted outcome of an action matches what actually happens?

Why it matters. It is our fourth research direction. Its only benchmark so far is forward's task 3, counterfactual order fills replayed from recorded Kalshi books, still a pipeline check, and nothing yet covers physical environments. Our position that models with similar validation loss can differ widely under intervention is untested.

Code and data. forward's task 3 (TASK3_FILLS.md) is a worked template: a deterministic replay, sampled actions, and models scored on what each action would have done. For physical environments, the cheapest ground truth is an environment that can be reset to an exact state and re-run under a different action: a deterministic simulator, a game engine, or a dataset with counterfactual outcomes such as CLEVRER.

First step. A one-page design: the environment, two or more models with matched validation loss, the consistency metric, and the gate.

Judged by. A pre-registered gate, for example: models within a stated margin on validation loss differ in consistency gap with a 95% interval excluding zero. If they do not, that is a negative result about our own position, and we publish it.
